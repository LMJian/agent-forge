# Code review and verification

Read [the runtime contract](../flow/references/runtime.md) and [review criteria](../../references/review-criteria.md). Run `next` for the selected `review` stage on the owning branch containing all module merges.

If the user asks to review existing changes and no task exists, configure actual project checks
and use `start-review --goal ... --base <explicit-baseline> --acceptance ...`.
Read the returned `review_context` instead of requiring absent intake or plan reports.
Do not create development-stage reports for work that happened outside this workflow.

Read `professional_method` from `next`. For `builtin`, perform the review below directly;
do not prepare a second capability invocation or launch another Codex session. For a selected
professional provider, use [capability handoff](../../references/capabilities.md):
`use-skill review --reason ...`, then `record-skill review --result ...`.
Confirm that reused native findings cover the current revision and scope. Carry native
Codex or professional review findings into the final Harness report rather
than performing a second full review to normalize them. Resolve findings and refresh affected
evidence before finalizing; code changes after completion require reopening review.

Read intake acceptance, planned verification and any selected design/scenario artifacts; review the diff from the recorded base SHA through HEAD and all relevant staged, unstaged and untracked changes. Light tasks use their compact approach and verification, without requiring missing design documents. Assess changed behavior and its necessary context; avoid unrelated historical cleanup. Cover correctness, security, concurrency, compatibility and operational risks as applicable. Record material coverage gaps honestly.

For remote targets, inspect/fix the diff and commit only the intended changes before final
verification and the review report. Follow `review_preparation` in the work packet. Local
review may remain uncommitted. This ordering avoids finishing a review that the required
delivery commit immediately invalidates.

Inspect `verify-plan`, then use `verify` for the selected batch. Run the critical path before
regression and packaging. Reuse eligible deterministic evidence under its declared policy;
see [focused tasks](../../references/focused-tasks.md). Do not rerun a batch merely for another
stage receipt. After fixes, reassess changed behavior and affected findings. If only Git
history changed, confirm the effective diff/inputs, reuse eligible checks and bind a new
report to current HEAD; do not restart the complete investigation or full semantic review.

Trace the accepted journey through its final observable side effect. Check the oracle and actual
environment for each step: file replay, source inspection and compilation cannot prove OS control,
background lifecycle or external persistence. Error-reporting/partial-output tests do not prove a
successful product outcome. Preserve unexecuted steps as pending or explicitly user-waived.

Write the report with an explicit findings array, code/evidence anchors and all required check receipt IDs. Complete `review` only with no unresolved blockers and fresh successful checks. A check's exit code establishes command success; assess whether its assertions actually cover the intended behavior.

If verification cannot converge within the retry budget, fail the stage with the observed cause and required decision. Do not increase limits or replace tests with no-ops to pass the gate.

Submit the stage result body with `submit --result FILE`; envelope fields and current command receipts are generated by the core. Continue with `next`.

For `profile=codex`, apply the shared [acceptance and verification contract](../../references/codex-workflow.md).
Keep command, agent and human evidence distinct; reuse that contract instead of loading another copy.
