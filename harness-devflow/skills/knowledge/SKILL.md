# Knowledge closure

Read [the runtime contract](../flow/references/runtime.md). Run `next` for the selected `knowledge` stage only when selected, after the chosen delivery endpoint. It is off by default.

Review the actual implementation, accepted review feedback, failure causes, verification results and user corrections. Distill only reusable facts with code/artifact evidence and applicability limits. Keep speculative lessons distinct from verified behavior.

Reuse the intake/recon baseline, selected design and review artifacts, and actual verification receipts. Cite the source artifact and relevant code revision for each retained discovery; distinguish pre-change facts from the implemented outcome. Check existing local notes with `knowledge-search` when overlap is likely, then retain only new or corrected reusable knowledge. Link the supporting baseline/scenarios instead of resummarizing the whole requirement, design or test suite. If nothing new remains, use `no_changes`.

Write Markdown notes in the run's artifact directory. Use `details.outcome = draft` for reusable notes or `no_changes` with a rationale when nothing warrants retention. `no_changes` uses `submit --result ...` immediately and creates no knowledge snapshot, even if review is configured.

For notes, the default is `submit --result ...`, which archives local copies without an extra approval prompt. If `workflow.knowledge_approval` is true, show the concrete notes, request approval, then record the actual user decision with `approve knowledge --actor ... --note ...`. `knowledge-search` returns archived notes with path/line evidence and `human_approved` provenance; never present automatic local notes as human approved.

Snapshots live in ignored `.harness/knowledge/`; they are not automatically committed, published or uploaded. If capture is inapplicable, skip with a reason. To resolve a pending gate, reopen with the actual decision before changing the outcome. End with the deliverable, verification results and real limitations.

Submit the stage result body with `submit --result FILE`; envelope fields and current command receipts are generated by the core. Continue with `next`.
