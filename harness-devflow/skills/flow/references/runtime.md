# Runtime contract

Resolve the plugin root from the loaded Skill. All command examples are suffixes of:

```text
python3 <plugin-root>/scripts/harness.py --repo <owning-checkout> --task <task-id> COMMAND
```

Use absolute paths for actual invocations. The CLI executes deterministic operations; the host's
Agent performs investigation, design, coding and semantic review. No separate model service is required.

## State and paths

```text
.harness/project.json                         # Project commands, host capabilities and policy
.harness/runs/<task>/state.json               # Core-owned project state and receipts
.harness/runs/<task>/artifacts/               # Documents and generated reports
.harness/runs/<task>/capabilities/<id>/        # Pinned professional method and request
.harness/runs/<task>/commands/<run-id>/        # Actual command/host requests and logs
.harness/worktrees/<task>/<epoch>/<module>/   # Builtin worktrees when selected
.harness/knowledge/<task>/<snapshot>/         # Optional reusable knowledge
```

A task belongs to its owning checkout and Git repository; branch may be null for detached HEAD.
Report/artifact paths stay inside the owning checkout. Native module worktrees can be elsewhere,
but the core verifies that they share the same Git repository and required base. State uses an
OS lock and atomic writes. Do not edit receipts, checkpoints, approval or stage status directly.

Current contracts: project config schema **2**, task state schema **3**, generated stage/module/
professional result schema **2**. Only current contracts are accepted. External command bridge
and delivery adapter protocols each use their separately documented schema **1**.

## Daily commands

```text
next
status
submit --result <stage-result-body.json>
plan --tasks <module-to-tasks.json>
checkpoint --module MODULE --step TASK --summary TEXT --check RUN_ID --artifact PATH
submit-module MODULE --result <module-result-body.json>
submit-batch --results <ordered-result-paths.json>
handoff --output <new-context-packet.json>
```

`next` starts a pending current stage and returns a bounded work packet. It never advances an
approval or marks a failed operation successful. Guided mode returns the next implementation
task; autonomous mode returns the module tasks and may submit several stage results in order.
`submit-batch` takes `{"results": ["path1.json", "path2.json"]}` and is autonomous-only. Each result
is independently validated and persisted; it stops at an approval. If a later result fails, inspect
`status`: the successful prefix remains completed. Batch submission never bypasses dependencies.

For Codex, `next` computes `plan` from the accepted intake `details.tasks`. For other profiles, `plan` takes a map from every module ID to tasks with `id`, `summary`, `acceptance` IDs and a
concrete `verification` method. It computes dependency waves and writes the plan report. It does
not create worktrees or choose an LLM. Missing/duplicate IDs, unknown dependencies and cycles fail.

## Stage result bodies

Write actual artifacts, then a JSON result body without `schema_version` or `stage`:

```json
{
  "status": "pass",
  "summary": "Describe the actual work and observed result",
  "artifacts": [".harness/runs/example/artifacts/design-audit.md"],
  "findings": [],
  "details": {}
}
```

`submit` fills the stage envelope and selects current successful check/adapter receipts. It does
not invent findings, acceptance coverage or successful verification. Every artifact is a nonempty
file and is hashed. Review and design audit need an explicit `findings` array. Findings contain
`severity: blocker | warning | suggestion` and `message`; a blocker needs actual resolution and
`resolved: true` before completion.

| Stage | Required result details |
| --- | --- |
| intake | `details.acceptance` IDs and `details.modules` with `id`, `depends_on`, `acceptance`, covering all criteria; `approach` if design is off; `verification` if test design is off |
| design | `details.designs` maps every module ID to a file also in `artifacts` |
| test_design | `details.scenarios` with unique `id` and `acceptance` mapping; expected outcomes belong in the artifact |
| plan | Generated by `plan --tasks`; concrete tasks and computed dependency waves |
| implement | Every module verified and integrated; cite the implementation results |
| review, integration | Actual successful configured checks for the current code; receipts may be explicitly supplied as `checks` |
| interfaces, push, pr, monitor, deploy | Matching real adapter result; `adapter_run` may be explicit; monitor requires observed `merged` |
| release | `details.checklist` for `verification`, `rollback`, `observability`, `risks`, each with `status: pass | not_applicable` and actual `evidence` |
| knowledge | `details.outcome: draft | no_changes` and the actual notes or rationale |

Modules use a result body without `schema_version` or `module`:

```json
{
  "status": "pass",
  "summary": "Implemented the observed behavior",
  "completed_tasks": ["persist"],
  "acceptance": ["AC-1"],
  "artifacts": [".harness/runs/example/artifacts/storage-results.md"],
  "checks": ["actual-current-module-receipt"]
}
```

Guided modules require ordered checkpoints for every planned task. Each checkpoint requires at
least one real passed module check and a result artifact. Final module completion requires all
configured review checks against the final bytes, even if earlier task checks passed. Historical
checkpoints describe previous increments; final checks validate their combined result.

## Execution evidence

```text
run-check unit
run-check unit --module storage
run-adapter push --authorization <existing-user-authorization>
prepare-module storage
attach-worktree storage --path <actual-host-worktree>
merge-wave
```

Read [host integration](../../../references/hosts.md) for provider selection. Both builtin and
native command execution return measured results bound to task, stage epoch, module, code
fingerprint, command configuration and logs. No command accepts a model-supplied exit code.
Checks that change tested bytes fail. Native bridge transport logs are retained separately.

Single-module checkout execution supports dirty working trees. Isolated worktrees require a
clean wave base and committed implementation for merging. Final local review/integration may
verify uncommitted bytes. Any subsequent commit or byte change invalidates code-bound evidence.
Opt-in deterministic local review checks may be explicitly reused across commits with identical inputs using `reuse-check`; the final review must still be reopened and bound to current HEAD. See [focused tasks](../../../references/focused-tasks.md). Remote delivery requires clean reviewed code. After naming a verified detached checkout with Git or the host, use `bind-branch --reason ...` to record the branch without changing its verified fingerprint. Review's configured age limit applies at push.

## Recovery, approval and delivery

```text
approve STAGE --actor <actual-person> --note <actual-decision>
reconcile-run RUN_ID --reason <observed-process-and-external-state>
reopen STAGE --reason <actual-change>
sync-config --reason <intentional-project-config-change>
configure-flow --target pr --reason <requested-deliverable>
skip STAGE --reason <actual-inapplicability>
fail STAGE --reason <observed-failure>
abort --reason <why-work-stops>
```

`submit` automatically prepares approval for a selected human gate. Present its concrete artifact
and record the actual applicable decision. Existing authorization is respected; a local actor/note
is an audit record, not an identity service. Guided checkpoints are automatic, not human gates.

A command can be passed, pending, failed, running or unresolved. An uncertain native execution or
external timeout blocks further mutations until reconciled. For interrupted running processes,
confirm both recorded processes have exited. `reconcile-run` records an inspected failure; it
cannot turn uncertainty into passed evidence. No executor fallback occurs after execution begins.

Stage/config changes preserve history and invalidate the affected suffix; they do not undo Git or
external effects. Assistance cannot change after module planning. A failed check or missing required
capability cannot be skipped as inapplicable. Only selected interfaces, integration and knowledge
support an actual applicability skip. Do not weaken the endpoint to evade its requirements.

`gate` verifies a current review before push. Optional `install-git-hook` refuses existing hooks;
compose `check-push` into a project hook manager when requested. Organizational enforcement belongs
in CI and the hosting platform. Native host permissions remain authoritative.

## Professional methods

```text
use-skill recon --reason <why-investigation-is-needed>
collect-recon --scope src --keyword contract
record-skill recon --result <professional-result-body.json>
```

Read the returned pinned Skill and request. Professional result bodies omit envelope fields;
`record-skill` binds them to the actual prepared invocation. The parent stage cites the resulting
artifacts and findings and uses `submit`. Preparation alone is not completion. Builtin methods
complete with their stage result. See [professional handoff](../../../references/capabilities.md).

CLI codes: success/pending observation 0; failed/unresolved execution or incomplete doctor 1;
invalid input, missing prerequisites or blocked state 2. Retry budgets are bounded. A native
scheduler/worker handle is accepted only after actual creation and does not prove completion.

## Focused entry and repository groups

`start-review --goal ... --base ... --acceptance ... [--target pushed]` reviews existing changes without development history. `context [--all] [--module ID]` reads artifact references; `ack-context CONTENT_ID` records actual reading only.

Group commands do not require `--task`: `link-repositories --manifest FILE`, `repositories-status GROUP`, `record-group-check GROUP --repository ID --run RUN_ID`. They keep each repository task independent and validate shared integration evidence; see [repository groups](../../../references/repository-groups.md).

## Codex default route

The `codex` profile adds a compact decision/feasibility/test/task packet, `verify`, `record-case`,
and `test-progress`. Read [the Codex contract](../../../references/codex-workflow.md) for fields and
semantics. `next` computes the plan from accepted intake tasks and prepares a selected design approval
from that same packet. New projects default to autonomous execution; existing task settings persist.
Current state schemas remain readable. Codex intake probes may run configured checks before planning.
Deterministic checks with explicit `reuse.across_stages=true` may be reused across same-checkout
implementation/review/integration; actual execution timestamps and all input/failure guards remain.
