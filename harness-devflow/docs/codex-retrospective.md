# Codex 工作流设计依据

Harness Devflow 将需求、可行性、验收和任务计划合并为一份决策包，减少重复文档与检查，
同时保留实际执行证据和明确的权限边界。本文说明这些机制解决的问题及其验证范围。

## 机制与目的

| 常见问题 | 对应机制 | 验证范围 |
| --- | --- | --- |
| 人工操作零散，无法判断剩余工作 | 场景声明 `command`、`agent` 或 `human`；人工项记录理由和批次 | `test-progress` 显示剩余用例、人工项和批次；不会代替执行 |
| 构建通过，但完整用户流程仍未验证 | 决策包声明 `journey`，产品场景通过 `steps` 映射全部步骤 | `proof` 区分运行时与文件产物，`oracle` 说明独立预期来源；编译不能替代运行时证据 |
| 核心技术假设在实现后才暴露问题 | intake 要求关键风险的实验、预期、观察和当前检查记录 | 未证明的关键风险阻止正式开发；实验是否代表真实场景仍需审查 |
| 相同决策在多个阶段重复编写 | 默认使用 Codex 精简流程，从决策包计算计划 | 保留需求、实现和最终审查的验收约束 |
| 相同输入反复运行耗时检查 | `verify-plan` 展示顺序、历史耗时和复用资格；`verify` 按层级执行 | 仅显式声明确定性的本地检查可复用；输入、环境、证据或时效变化使复用失效 |
| 为方便隔离而擅自切换开发环境 | 默认使用当前分支和 checkout；分支或工作树操作先记录明确用户授权 | 运行时检查自身的工作树创建和分支绑定，Agent 同时约束外部 Git 操作 |

## 完整流程与证据边界

验收从实际用户入口追踪到最终可观察结果，包括必要的系统交互、后台处理与持久化。
小型库变更可以只有一个公共入口步骤；包含多次交接的功能必须覆盖全部必要步骤。
文件回放、源码检查和编译分别证明有限的边界，不能推断未经执行的运行时行为。

已知失败应优先使用保留的输入与独立预期验证。能获得旧版本时，确认用例能够检出旧失败，
再验证修复结果。只证明可恢复错误或部分输出的用例，不能用于证明完整成功结果。
用户确认的结果与 Agent 实际执行的检查分别记录；交付后发现的失败也可以使完成态失效。

无法执行的场景保持待验证或阻塞。只有用户明确取消的要求可以记录为排除，排除不计为通过。
GUI、设备、部署等操作遵守适用的授权规则，工作流配置本身不授予操作权限。

## 检查效率

先运行真实入口或已知失败的关键检查，再运行回归和打包检查。配置层级时需保留构建产物
依赖；同层级保持配置顺序。历史耗时用于估算已知命令成本，不包含未知检查或人工操作。

同一运行中的 checkout 模块可复用自己的确定性检查；跨阶段复用需显式声明
`across_stages`。复用保留原执行时间和日志，不伪装成新执行。设备、网络、签名和环境状态
可能改变结果，不能仅凭源码相同就认定检查可复用；需要重新执行时使用 `--fresh`。

## 回归与限制

回归测试覆盖公开 CLI 流程、关键风险探针、产品证据边界、验收步骤覆盖、人工项要求、
授权检查、失败后的状态变化，以及检查复用、失效和强制重跑。分支测试只操作一次性测试仓库。

运行时验证结构、覆盖关系、输入一致性和证据有效期。Agent 仍需审查断言、独立预期和
实际环境是否足以证明功能；插件测试通过不等于使用插件开发的产品已通过验收。

[分支授权规则](../references/branch-consent.md) 和 [决策包示例](codex-packet.example.json)。
