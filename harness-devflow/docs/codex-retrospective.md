# 卷轴项目复盘：缩短流程而不降低验收标准

## 证据与原因

依据本次对话、卷轴本地 Harness 状态和插件实际代码；没有重跑手机操作或修改卷轴数据。

| 观察 | 已确认的机制问题 | 修复 |
| --- | --- | --- |
| 多次人工录屏、解锁、回复帧数/尺寸，用户反复询问剩余数量 | test_design 只校验 id 与 acceptance，没有执行者、自动化约束和执行台账 | 明确 command/agent/human；人工理由和批次；持续显示剩余用例 |
| 主功能仍不可用，但已有大量测试和构建成功 | review 只验证配置的检查命令；未强制产品路径验收 | Codex 每个验收条件必须覆盖产品级用例，待执行/失败/过期不能完成 |
| 更换算法后仍需用户发现问题 | intake/design 不要求关键假设的实际运行证据 | 技术风险进入 intake；关键风险必须有当前实验收据和观察，未证明即阻断 |
| 每个里程碑重复编写多份文档，guided 逐任务记录 | 默认 standard + guided，默认七个研发阶段，批准/集成再增加 | Codex 默认三段工作、四个内部状态；一个决策包自动计算计划 |
| M2、M3 重复执行同一代码的检查 | module / review / integration 证据隔离；旧 reuse 仅 review→review | 明确 opt-in 的同 checkout 跨阶段复用和一次 verify 批处理 |

在当前保存的状态中：M2 有 21 次检查，其中同名、相同代码指纹的成功检查重复 7 次；
M3 发布准备有 28 次检查、重复 15 次；M3 分发有 25 次检查、重复 7 次。
这是可调查的重复数量，**不代表这些全部都可以安全复用**：签名、归档、设备、网络和忽略文件
可能是额外输入，需逐项声明。M0 也有 98 次程序检查；不能将此次经历描述为“所有测试都是人工”。
实际问题是人工操作过细、未集中读回、缺少稳定进度，以及程序检查没有证明关键产品目标。

也包含执行层面的失误：把底层检查通过扩大成产品可用结论、将可自动读取的结果反复交给用户反馈，
不能全部归因于工具。此次同时修改执行指导与运行时约束，约束 Codex 的后续行为。

## 新默认路径

需求/架构/可行性/验收/任务合并为一份 packet → 连续实现 → 产品自测与交付。
默认不新增专业服务、模型路由、常驻调度、多 Agent 或批量人工验收。
风险较高的功能先验证一个可用的垂直切片：例如录屏→识别→拼接→预览的真实输入结果，
而不是分别验证“能录到帧”“库能调用”“文件能生成”之后推断整体可用。
GUI 仍遵守用户明确批准，Apple 权限/真机物理操作不能承诺全自动。

如果一次试验不能证明核心路径，继续完成有限的技术实验，或与用户确认明确缩小范围；
不提前扩展完整产品。修复既有失败时复用实际输入；同时比较已知可行的原生/开源替代方案。
程序能验证记录完整性，不能自动判断研究覆盖是否充分、图片质量是否正确，Codex 仍负语义审查责任。

## 自动回归覆盖

新增回归覆盖公开 CLI 的短流程、关键风险未证明、伪造/过期探针、单元级证据冒充产品证据、
人工项遗漏、明确取消、审批不能跳过、代码修改使结果失效、失败检查、跨阶段复用和强制重跑。
另保留现有真实 Git/工作树/收据/发布边界回归。验证及安装结果另记在本次交付记录中。

本次不修复卷轴算法，不改写已完成的卷轴任务，不把插件测试通过等同于下一次项目一定没有返工。
